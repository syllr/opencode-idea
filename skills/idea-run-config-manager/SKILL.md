# idea-run-config-manager — run configuration 管理(全生命周期)

## 定位与管辖文档

本 skill 管本项目 **run configuration 这件事本身**:哪些流程该固化成一个配置、怎么建、怎么跑、怎么停、怎么重启。

- **只管非长驻的固定流程**(迁移 / 同步 DDL / 生成代码 / 打包 / 装依赖 …)。**长驻应用**经哪个配置启动、端口、热重载归 `idea-standalone` skill 的块 —— 两边**不要互相抄**:那边已经写了的不在这里重写,这里写了的那边不重复。
- **产物位置固定:项目根 `AGENTS.md`**,作为其中一块,用 `<!-- idea-run-config-manager:begin -->` 与 `<!-- idea-run-config-manager:end -->` 包裹。
  放在这里是因为根 `AGENTS.md` 是 AI 在本项目工作时必读的文件 —— 于是"本项目已经固化了哪些流程、这些配置怎么跑"下一次会被自动读到,
  **不用重新问一遍、也不会重复建同一个配置**。这是本块存在的全部理由:它记的是**结论**,不是通用判据。
- **标记之内由本 skill 生成与维护;标记之外的项目内容一律不动** —— 尤其**不要触碰**其他 skill 的标记块(`idea-standalone` / `project-scaffold`)。
- **目标产物的骨架、各段约定与写作规范以 [assets/AGENTS.template.md](assets/AGENTS.template.md) 为准**,本 skill 不另行维护章节骨架或逐段规则;
  生成或更新前必须先读该文件,并严格沿用其中的标题层级、标记与生成提示。
- 只对这个项目生效;**不写**全局配置目录 (`~/.config/opencode/`),也不另建规则文件。

## 判据:该不该建

判据只有一条:**这件事以后会不会以同样的形态再发生?**

- **会 → 该固化,而且你必须主动提**。典型信号:用户让你做的是**重复性动作**,还会对别的环境 / 别的分支 / 下一次改表再做一遍 ——
  同步某个环境的 DDL、跑数据库迁移或回滚、生成代码、打包、按固定步骤清洗数据。
  - **别默默每次手搓命令**:那样下次还得从头猜一遍;
  - **也别自己动手建**:**先把方案摊开问用户** —— 配置名、实际执行的命令(`scriptText`,或它指向的 `scriptPath`)、工作目录、为什么值得留。
    **同意才建**;用户说这次先这样,就照办,别再追着问。
- **不会 → 用原生 `shell` 直接跑,别建**。这就是两者的分界线:原生 `shell` 是**就地执行、用完不留痕**(命令只存在于会话里);
  建配置是**把命令落盘成 `.run/<name>.run.xml`、往后反复用**。一次性的、探索性的、调试性的、参数每次都不一样的一次性操作,
  走 `shell` 跑完算 —— 建配置只是给项目留垃圾。
- **建之前先查,防泛滥**:先查已有配置(见下),有同类就**复用**;同一件事**不要按参数 / 按文件 / 按环境拆成一堆配置**,
  变化的入参用单次覆盖。一个项目通常就那么**几个**;数量明显长起来就是滥用信号。

## 读取

- **工具名前缀跟着项目走**:本项目的工具前缀由它接入时的名字决定 —— root 是 `ide`,子项目是它的目录名。下文的 `<前缀>_` 就是它
  (例如 `ide_get_run_configurations` 或 `modelserver_get_run_configurations`)。
- 读 `<项目根>/AGENTS.md`,确认是否已存在 `idea-run-config-manager` 标记块(更新)或需要在文件末尾追加(新增)。
- **该项目的 `<前缀>_get_run_configurations` 直接调用,不传任何参数** → 项目里已有的 run configuration 就是**用户已经在 IDEA 里配好的那些**,
  这一次调用把它们的名字连同启动细节(程序参数、工作目录、环境变量、是否支持启动时覆盖)一并给出。
  它是"哪些流程已经固化"的**唯一来源** —— 不需要、也不要再去逐个翻 `.run/*.run.xml`,那份列表已经是配置的结果。
- 也读一下 `idea-standalone` 的标记块(如果有):长驻应用列在那里,**本块不重复**。
- 补齐缺口:哪些流程确实会重复发生、归哪个配置、参数怎么给、什么时候跑 —— **逐条向用户确认**,不猜。

## 建与更新

1. 确认该建之后,先 `get_run_configurations` 查重,再把方案问过用户,才动手建。
   `<前缀>_create_shell_run_configuration` 只支持 **Shell 类型**,`configurationName` + `scriptPath` / `scriptText` / `cloneFrom` 三选一;
   **其他类型请用户在 IDEA 里建**。
2. **配置一律不由你手写**:不要写 `.run/*.run.xml`(写错 `type` IDE 会**静默忽略整个文件、日志里也不报**),也不要手搓启动命令。
   建完用 `<前缀>_get_run_configurations` 复查一次,确认它真的出现了。
3. 归属判断:属于本块骨架的内容写进 `idea-run-config-manager` 标记块;不属于的(项目自己的其它纪律)留在标记外,本 skill 不写。
4. 先读 [assets/AGENTS.template.md](assets/AGENTS.template.md),按其中的生成提示逐段填充。**`<!-- 生成提示:begin -->…<!-- 生成提示:end -->` 是给生成过程的说明,产物里整块删掉** ——
   产物是给 AI 当规则读的,里面不该留指令。同时:**未涉及的表格行与小节整块删掉**,不留空标题、不留 `{...}`。
5. **新增**(文件里还没有标记块):在 `AGENTS.md` **末尾追加**标记块,文件既有内容原样保留;文件不存在则创建它。
   只替换标记内内容、不动标记外 —— 尤其**不要触碰**其他 skill 的标记块。
6. **更新**(已有标记块):只替换 `<!-- idea-run-config-manager:begin -->` 与 `<!-- idea-run-config-manager:end -->` 之间的内容,块外一字不动。
7. 用原生 `edit` 做定向替换;文件不存在时才用 `write` 创建。**不要整文件重写**。
8. 复读并核对:标记块内逐段与模板一致,块外内容与改动前逐字一致,报告产物清单。

## 运行期:跑 / 停 / 重启

- **一次性 Job 型配置**(迁移 / 生成 / 打包这类,**跑完自己就退**)→ `<前缀>_execute_run_configuration`;需要项目环境的命令也走这一条。
- **长驻进程**(起来就不退)→ `<前缀>_rerun_run_configuration`(在跑就重启、没在跑就启动),**不要**用 `<前缀>_execute_run_configuration` ——
  它是 Run 路径,会起出**重复实例**;细则见 `idea-standalone` 的块。
- **停** → `<前缀>_stop_run_configuration`(停掉该配置的**全部**实例并等它们退出,幂等,没在跑也返回成功)。
  **不要** `kill` / `pkill`:外部杀掉的进程 IDE 并不知道,Run 窗口仍显示运行中,下次启动就会撞端口。
- 停 / 重启前后先用 `<前缀>_list_running_configurations` 看**真实状态**(几个实例 / 各自 pid / 退出码),别凭 Run 窗口的显示判断。
- 工具列表里没有这一组工具(没装配套插件 `idea-mcp-enhance`)**交给用户**:请他在 IDEA 里手动建 / 跑 / 停 ——
  AI 既不手搓命令,也不手写 `.run/*.run.xml`。
