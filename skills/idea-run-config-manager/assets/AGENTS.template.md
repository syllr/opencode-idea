# run configuration 档案

<!-- 生成提示:begin -->

标记之外是项目自己在 `AGENTS.md` 里维护的内容,本 skill 一律不动;也只写这个项目 —— 不写全局配置目录,不另建规则文件。
`{...}` 是待替换的元变量,不留进产物。未涉及的条目与小节整块删掉,不留空标题。 **`<!-- 生成提示:… -->`
是给生成过程的说明,产物里整块删掉** —— 产物是给 AI 当规则读的,里面不该留指令。
<!-- 生成提示:end -->

本项目里 **除服务化应用之外**的 run configuration:每个配置 **是什么、怎么跑、什么时候跑**;服务化 (长驻应用)的配置登记在
`idea-standalone` 块里,不在这里。

**谁能起它,只有三种** —— 读这个块的人照它决定动不动手:

- **用户手动触发**:用户自己在 IDE 里跑,AI **完全不碰**。这类只登记在末尾「用户手动触发」一节, **只有名字**,没有别的说明。
- **用户授权触发**:用户开口之后 AI 才跑 (用户也可以在这个会话里一次性授权); **AI 不自己挑时机**。
- **AI 自己触发**:AI 判断到场景就自己跑;这类条目的 `when` **必须把那个场景写具体**。

## run configuration 一览

<!-- 生成提示:begin -->

**先过滤**:动手前读 `<项目根>/AGENTS.md` 里 `idea-standalone` 的标记块,把它登记过的 run configuration 名字收集起来 ——
**这些一律不进本块**(它们服务化 / 长驻,端口与热重载已在那边写清)。剩下的才是本块内容;没有那个块就不过滤。
**枚举以工具为准**:各项目各有自己的工具前缀 (root 是 `ide`,子项目是它的目录名),看哪个项目就用 **它自己那个前缀**
的工具 —— `<前缀>_get_run_configurations` 直接调用,不传参数,它给出 IDE 真正认的配置 (含存在 `.idea/` 里的那些,单翻
IDE 自己存储里 (不在项目目录)的那些看不到)。 **项目与各子项目里真正存在的、过滤后剩下的都要有。**
**项目写在标题的括号里**(那套工具的前缀:root 写 `ide`,子项目写它的目录名):一条配置属于谁、该用哪套工具去看和跑,由它决定。
标题里的配置名必须是该前缀下 **真实存在的名字**,不凭印象写;块里有、项目里已经没有的 **整个条目删掉**。 **只登记
base,变体不另起条目**:run configuration 的名字是 `[os@]base[@env]`,`@` 分割、最多三段 —— os 段 (`win` = Windows,缺省 =
macOS/Linux)、
base 段 (配置本体)、env 段 (环境名,缺省 = 所有环境通用这一套)。`win@base` 与 `base@env` 都是 **同一个 base 的变体**:
平台不同 / 环境不同,事情是同一件。 **本块只登记 base**(`{配置名}` 不带任何 `@` 段),变体不另起条目 ——
把"有哪些变体"写进 base 的 `desc` 一条即可。
判断这条流程在哪个平台成立 **看命令与脚本内容本身**(命令里有 `\` 路径、调用 `.bat`、依赖 Windows 专属工具的,就是 Windows)。
**判断不了就问用户**,不猜。

**when** 写 **谁能起它、什么场景起它** —— 会进这份列表的只有两种,写明是哪一种:

- **用户授权触发**:用户开口 (或在本会话里授权)之后 AI 才跑;后面写用户通常在什么情况下会要它跑 (发版前 / 出安装包 /
  回归)。
- **AI 自己触发**:AI 判断到这个场景就自己跑;后面 **必须把场景写具体**(改完某类代码要生成代码 / 改了依赖要装依赖 / 改了
  schema 要同步某个环境的 DDL),不写"需要时""合适时"。

第三种 —— **用户手动触发**(用户自己在 IDE 里跑、AI 完全不碰)**不要写进上面的条目**,登记到末尾「用户手动触发」一节,只写名字。
判断不了就问用户。 **有副作用的流程 (改远端、动数据、出产物)说不清场景就别标成 AI 自己触发** —— 归"用户授权触发"。

**每一项都有两种写法,逐项判断,不要给整条定一个"简单/复杂"模式**:

- **行内形态** —— 这一项只有一句话:写在项名同一行,`when:用户授权触发 —— 改了 x 后 y`。
- **子列表形态** —— 这一项有好几条 (多个触发条件 / 多个步骤 / 多个结果 / 多个事实):项名冒号后留空,缩进两个空格各起一条
  `-`。

所以同一个条目里 **混着两种写法是常态**,下面三种都可以:

| 情况     | 长什么样                                       | 典型配置                                       |
| -------- | ---------------------------------------------- | ---------------------------------------------- |
| 全行内   | 五项各一句,没有任何子项                        | 跑完即退、一句话能说清的命令(推迁移、跑生成器) |
| 全子列表 | 五项里多数各有多条                             | 带产物、要同步、要重启的构建 / 部署类          |
| 混合     | 例如 `when` 一句行内、`after run` 三件事拆三条 | 最常见 —— 只看**那一项自己**有几句             |

判断只看"这一项有几句话",与配置本身复杂不复杂无关;别为了整齐把一句硬拆成几条,也别把五六条压成一行。也可以只对少数项例外:
`before run:无(脚本自己跑 mvn package)` 这种一句带解释,就留在行内。

示例 (混合形态):

```markdown
- `connector-build`(项目 ide)
    - when:AI 自己触发
        - 改了 `poc/文件数据源解析与检索/解析程序` 下的 Java 源码后,重新出连接器 jar 并装进
          `middleware/seatunnel/connectors/`
    - before run:无 (脚本自己跑 mvn package)
    - run:ide_execute_run_configuration
    - after run:
        - 产物 `middleware/seatunnel/connectors/connector-fileparse-<ST 版本>.jar`(78M,已 gitignore)
        - 接着同步到部署机:`ide_upload_to_deployment`,`serverName` 传 `mbpmiddleware`、`mode` 传 `upload`(默认 `mirror`
          会删远端多余文件,别用);`in_progress` 就按 handle 轮 `ide_get_deployment_task_status`
        - 同步完在部署机上 `docker compose restart seatunnel`
    - desc:
        - 一条命令完成「构建 → 拷进 connectors → 打印 md5 并与 compose 引用比对」
        - 产物改名会在输出里点名 compose 失配;脚本本身不管同步与重启
```

示例 (全行内形态,同一块里出现很正常):

```markdown
- `db-migrate`(项目 ide)
    - when:用户授权触发 —— 改了 `packages/db` 的 schema 后要重新生成客户端并推迁移
    - before run:无
    - run:ide_execute_run_configuration
    - after run:数据库结构更新,生成的客户端代码落在 `packages/db`
    - desc:先 `pnpm -C packages/db generate` 再 `migrate:deploy`;动远端数据,不由 AI 自行触发
```

**before run** 写 **跑之前要先做的事**(先装依赖 / 先构建 / 先起某个服务):**一条一步,按顺序排**。 **多数没有 —— 写 `无`**
(这一项始终在,别省略)。前置事项往往 **不是**一个 run configuration (没有对应配置),所以只能写在这里 ——
漏了它,照着本块跑的人会直接跑出一个起不来的流程。 **run** 写走哪条工具:跑完即退的用 `<前缀>_execute_run_configuration`
;长驻进程用 `<前缀>_rerun_run_configuration`(在跑就重启、没在跑就启动)。 **不要**用 `execute` 跑长驻进程 —— 它是 Run
路径,对常驻进程 **它会起出重复实例**。 **after run** 写 **跑完之后的结果**:**产物落在哪**(路径 / 文件名 / 被谁读走)一条,
**接下来要不要做什么**(要发布 / 要同步到某台机器 / 要重启什么 / 什么都不用做)一条。 **没有产物、跑完就完的,写 `无`。**
**desc** 是这个条目唯一的自由文本项:**它是什么、干什么的**(同步某个环境的 DDL / 生成代码 / 跑迁移 …)一条,有什么坑
(必须先备份 / 只对某个环境生效 / 幂等与否 …)一条。
分两件事都往这里写, **不要再开新项**。 **有 `@` 变体就在这里补一条**:有哪些变体 (如 `console-web@yutao`)。
写清它到底跑什么命令,就调 `<前缀>_inspect_run_configuration` 看它的内容,拿不准就 **问用户**,不猜。
本块的 **主要价值**就在 **desc** 与 **before run**:下次要办同类事情先在这里搜关键词,找得到就直接用,
**不要再建一个重复的**。 **目录、端口这类"配置里本来就有"的字段不要抄进来** —— 它们会跟配置变旧而对不上;确实要交代依赖关系,就写进
`desc` 或 `before run`。 **五项的名字与顺序不要改**(`when` / `before run` / `run` / `after run` / `desc`),并且 **与
`idea-standalone` 应用表的列同名同序**(`before run` / `run` / `after run` / `desc` 这四项两边一致);本块多 `when`,那边多
`app` / `run configuration` / `port`(服务化应用就是"改完代码要起它来测"的时候起,没有别的时机可写)。 **五项始终都在**:
`before run` / `after run` 真没有内容就写 **`无`** —— 不省略,也不写 `-` / `N/A`。
