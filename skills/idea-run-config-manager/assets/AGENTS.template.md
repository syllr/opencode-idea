# run configuration 档案

本项目里 **除服务化应用之外**的 run configuration:每个配置 **是什么、怎么跑、什么时候跑**;服务化 (长驻应用)的配置登记在
`idea-standalone` 块里,不在这里。 **配置增删改之后,本块要跟着加 / 删 / 改条目** —— 做法见 `idea-run-config-manager` skill;
块里和项目对不上,比没有块更糟。

**谁能起它,只有三种** —— 读这个块的人照它决定动不动手:

- **用户手动触发**:用户自己在 IDE 里跑,AI **完全不碰**。这类只登记在末尾「用户手动触发」一节, **只有名字**,没有别的说明。
- **用户授权触发**:用户开口之后 AI 才跑 (用户也可以在这个会话里一次性授权); **AI 不自己挑时机**。
- **AI 自己触发**:AI 判断到场景就自己跑;这类条目的 `when` **必须把那个场景写具体**。

## run configuration 一览

**「怎么读配置名」与「怎么选变体」两节是固定文本,照抄,不要改写、不要删条目** —— 它们是读名字与选变体的规则,下面那个列表靠它们才成立。

<!-- 生成提示:begin -->

**先过滤**:服务化 / 常驻应用的配置 **一律不进本块**(它们归 `idea-standalone`,端口与热重载写在那边)。有
`idea-standalone` 的标记块时,再把它登记过的名字一并排除;没有那个块也照样按性质过滤。
**枚举以工具为准**:各项目各有自己的工具前缀 (root 是 `ide`,子项目是它的目录名),看哪个项目就用 **它自己那个前缀**
的工具 —— `<前缀>_get_run_configurations` 直接调用,不传参数,它给出 IDE 真正认的配置 (含存在 IDE 自己存储里、不在项目
目录的那些 —— 翻文件看不到)。 **项目与各子项目里真正存在的、过滤后剩下的都要有。**
**项目写在条目开头的括号里**(那套工具的前缀:root 写 `ide`,子项目写它的目录名):一条配置属于谁、该用哪套工具去看和跑,
由它决定。条目里的配置名必须是该前缀下 **真实存在的名字**,不凭印象写;块里有、项目里已经没有的 **整个条目删掉**。 **只登记
base,变体不另起条目**:run configuration 的名字是 `[os@]base[@env]`,`@` 分割、最多三段 —— os 段 (`win` = Windows,缺省 =
macOS/Linux)、
base 段 (配置本体)、env 段 (环境名,缺省 = 默认环境)。`win@base` 与 `base@env` 都是 **同一个 base 的变体**:
平台不同 / 环境不同,事情是同一件。 **本块只登记 base**(`{配置名}` 不带任何 `@` 段),变体不另起条目 ——
把"有哪些变体"写进 base 的 `desc` 一条即可;判断某个变体在哪个平台成立 **看命令与脚本内容本身**(有 `\` 路径、调用
`.bat`、依赖 Windows 专属工具的,就是 Windows), **判断不了就问用户**,不猜。

**when** 只写两种,先把是哪一种写明:**用户授权触发** → 用户开口 (或在本会话里授权) 之后 AI 才跑,后面写用户通常在
什么情况下会要它跑 (发版前 / 出安装包 / 回归);**AI 自己触发** → AI 判断到场景就自己跑, **必须把场景写具体**(改完某类代码要
生成代码 / 改了依赖要装依赖 / 改了 schema 要同步某个环境的 DDL),不写"需要时""合适时",有副作用又说不清场景的一律归
"用户授权触发"。第三种 **用户手动触发**(用户自己在 IDE 里跑、AI 完全不碰) **不写进条目**,登记到末尾「用户手动触发」
一节,只写名字;判断不了就问用户。

**每一项都有两种写法,逐项判断**(别给整条定一个"简单 / 复杂"模式):只有一句话 → 写在项名同一行 (`when:用户授权触发 ——
改了 x 后 y`);有好几条 (多个触发条件 / 多个步骤 / 多个结果) → 项名冒号后留空,缩进两个空格各起一条 `-`。同一个条目里
**混着两种写法是常态** —— 只看 **那一项自己** 有几句,与配置复杂不复杂无关;别为了整齐把一句拆成几条,也别把五六条压成一行
(`before run:无 (脚本自己跑 mvn package)` 这种一句带解释的,就留在行内)。

示例 (混合形态):

```markdown
- `connector-build`(项目 ide)
    - when:AI 自己触发
        - 改了 `poc/文件数据源解析与检索/解析程序` 下的 Java 源码后,重新出连接器 jar 并装进
          `middleware/seatunnel/connectors/`
    - before run:无 (脚本自己跑 mvn package)
    - run:ide_execute_run_configuration
    - after run:
        - 产物 `middleware/seatunnel/connectors/connector-fileparse-<ST 版本>.jar`(78M,已 gitignore)
        - 接着同步到部署机:`ide_upload_to_deployment`,`serverName` 传 `mbpmiddleware`、`mode` 传 `upload`(默认 `mirror`
          会删远端多余文件,别用);`in_progress` 就按 handle 轮 `ide_get_deployment_task_status`
        - 同步完在部署机上 `docker compose restart seatunnel`
    - desc:
        - 一条命令完成「构建 → 拷进 connectors → 打印 md5 并与 compose 引用比对」
        - 产物改名会在输出里点名 compose 失配;脚本本身不管同步与重启
```

示例 (全行内形态,同一块里出现很正常):

```markdown
- `db-migrate`(项目 ide)
    - when:用户授权触发 —— 改了 `packages/db` 的 schema 后要重新生成客户端并推迁移
    - before run:无
    - run:ide_execute_run_configuration
    - after run:数据库结构更新,生成的客户端代码落在 `packages/db`
    - desc:先 `pnpm -C packages/db generate` 再 `migrate:deploy`;动远端数据,不由 AI 自行触发
```

**before run** 写 **跑之前要先做的事**(先装依赖 / 先构建 / 先起某个服务), **一条一步、按顺序排**;多数没有 —— 写 `无`
(这一项始终在)。这些事往往 **不是** run configuration,只能写在这里;漏了它,照本块跑的人会直接跑出一个起不来的流程。
**run** 写走哪条工具:跑完即退的用 `<前缀>_execute_run_configuration`;长驻进程用 `<前缀>_rerun_run_configuration`
(在跑就重启、没在跑就启动)。 **不要**用 `execute` 跑长驻进程 —— 它是 Run 路径,对常驻进程它会起出重复实例。
**after run** 写 **跑完之后的结果**:产物落在哪 (路径 / 文件名 / 被谁读走),接下来要不要做什么 (发布 / 同步 / 重启);
**没有就写 `无`**。 **desc** 是唯一的自由文本项:它是什么、干什么的一条,坑 (要先备份 / 只对某个环境生效 / 幂等与否) 一条,
**有 `@` 变体也补一条**, **不要再开新项**。写不清它到底跑什么命令,就用 `<前缀>_inspect_run_configuration` 看它的内容,
拿不准 **问用户**。 **desc 与 before run 是本块的主要价值**:下次办同类事情先在这里搜关键词,找得到就直接用,
**别再建一个重复的**。 **目录、端口这类配置里本来就有的字段不抄进来** —— 会跟配置变旧而对不上;要交代依赖关系就写进
`desc` / `before run`。 **五项的名字与顺序不要改**(`when` / `before run` / `run` / `after run` / `desc`),并与
`idea-standalone` 那个块 **同名同序**(`before run` / `run` / `after run` / `desc` 四项一致);本块多 `when`,那边多
`应用` / `端口` / `热重载`。 **五项始终都在**:真没有内容就写 **`无`** —— 不省略,也不写 `-` / `N/A`。

### 怎么读配置名

run configuration 的名字是 `[os@]base[@env]`,`@` 分割、最多三段:`os` = `win`(缺省表示:macOS / Linux)、`base` = 配置本体
(必填)、`env` = 环境名(缺省表示:默认环境)。`win@base`(换平台)与 `base@env`(换环境)都是 `base` 的 **变种**:
同一件事,平台 / 环境不同。 **只登记 base**,变体不另起条目 —— 有哪些变体写进 base 的 `desc`。

### 怎么选变体

- **平台**:macOS / Linux 用 `base`,Windows 用 `win@base` —— `win@base` 不存在就 **交回用户**,别拿 base 顶替。
- **环境**:只有一套 (`base` 与 `base@<env>` 里只有一个存在)→ **直接用,不问**。两套同时存在 (`test` 与 `test@dev`:
  前者是默认环境,后者是 `dev` 环境)→ **启动前问一次用户走哪个环境**;选定后本会话默认走这套,别反复问 —— 改代码 →
  自己重启 → 同一套变体。
- 一个环境怎么接上 (启动参数 / 环境变量 / 配置文件) 是项目自己的事:照现成的同类变体来,或问用户。

### base 登记

- {配置名} (项目 {前缀})
    - when:{用户授权触发 / AI 自己触发} —— {什么场景}
    - before run:{第 1 步 / 第 2 步 / 无}
    - run:{<前缀>_execute_run_configuration}
    - after run:{产物落在哪 / 接下来要做什么 / 无}
    - desc:{它是什么 + 有什么坑 + 有哪些 @ 变体}
