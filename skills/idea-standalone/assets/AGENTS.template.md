## 一、什么是 standalone 模式

**standalone = 启动收口只有 IDEA run configuration** —— 每个应用的启动入口是 IDEA 的 run configuration (Run / Debug)
,不是手搓命令行;至于配置内部怎么起 (**本机进程 / 容器 / 部署到远端**)
,由它自己决定,本段不预设。给"本项目怎么起、起在哪"下定义,至少覆盖:

- **入口唯一 (唯一绝对的约束)**:每个应用的启动入口就是 IDEA 的 run configuration, **不是手搓命令行**。
- **形态不限**:配置可以起本机进程,也可以是容器 (Compose / K8s)、或部署到远端 —— 怎么起是配置的事,
  **不要假设它一定在本机直跑**。相应地,哪些应用 **不在本机跑、或本机起不来**要单独写明 (需要 GPU
  的服务、本机直连的远端数据库、只能部署后验证的服务),别当成"本机直跑"来验证。
- **只启动其中一部分是常态** —— 不要求所有应用都起来,用户可能只开一两个。
- **跑应用只用 `<前缀>_rerun_run_configuration`**:在跑就重启、没在跑就启动 —— 不必分辨"这是启动还是重启",直接 rerun 就完事。
  常驻进程化 / 服务化的 run configuration 一律走这一条。
- **不要用 `<前缀>_execute_run_configuration` 跑这些应用**:它是给 **命令 / Job 类型**的配置跑的,standalone 的配置是
  **常驻型**(起来就不退),
  用它只会起出重复实例。
- **也不要绕过 IDEA**:不用 `go run` / `pnpm dev` / `uvicorn` / `python -m ...` 这类裸命令起进程,更不要 `kill` / `pkill`
  业务进程 ——
  外部杀掉的进程 IDE 并不知道 (Run 窗口仍显示运行中,下次启动就撞端口)。
- **重启不必先问**:改完代码要重启哪个应用,直接 `<前缀>_rerun_run_configuration` —— 这条链是无人化的,先征求同意只会把重启卡住。
- 工具列表里没有 `<前缀>_rerun_run_configuration` 时 (没装配套插件):交回用户,请他在 IDEA 里手动跑,AI 不动手。
- **与部署链纪律互不构成许可**:本段管的是 **standalone 跑应用的方式**
  ,不适用于部署流程;反过来,部署链里的步骤也不构成"可以绕开本段、用裸命令在本机起应用"的许可 —— 两阶段纪律互相独立。

## 二、standalone 下启动哪些应用 (必须经 IDEA run configuration)

**「怎么读配置名」与「怎么选变体」两节是固定文本,照抄,不要改写、不要删条目** —— 它们是读名字与选变体的规则,下面那个列表靠它们才成立。

<!-- 生成提示:begin -->

一条一个应用。 **条目开头的 `{base 名}` 填真实配置名**(不带任何 `@` 段)—— 平台与环境由名字里的段决定,见上面「怎么读配置名」。
**变体不另起一条**:`win@base`(换平台)、`base@env`(换环境)都是同一个 base 的变种,写一条就够,怎么选走「怎么选变体」那节。

**下面是两个示例**,照这个形状写 —— 一条把长的地方展开,一条全是短句 (生成产物时把示例删掉):

- `console`(项目 ide,`console-web`)
    - before run:先起 platform-server:`/api` 代理到平台服务端地址
    - run:ide_rerun_run_configuration
    - port:5173,被占用时 Vite 自动顺延
    - 热重载:有(Vite HMR) —— 改前端源码自动热更新,无需重启
    - after run:无
    - desc:前端控制台 (React + Vite dev server)

- `platform`(项目 ide,`platform-server`)
    - before run:
        - 确认 Tailscale 已连到 yutao-mac
        - 确认 apps/platform/.env 存在
    - run:ide_rerun_run_configuration
    - port:8080,被占用即启动失败
    - 热重载:有(`node --watch` 自动重启);改了 .env 或依赖才需重启
    - after run:无
    - desc:平台服务端 (Node + Fastify);起不来时先查 Tailscale 与 .env

`run configuration` **必须是 `<前缀>_get_run_configurations` 里真实存在的 base 名**,不凭印象写;缺配置就
**先问用户要不要建**,
再用 `<前缀>_create_run_configuration` 建 (建之前把"配置名、干什么、为什么值得留"摊开给用户看,同意才建);工具列表里没有它时,
请用户自己在 IDE 里建。不要手搓启动命令,也不要自己写配置文件。 **before run** 写 **跑之前要先做的事**:**多数应用写 `无`**
(这一项始终在,不留空)。只有确实"得先做点什么才能起"时才写,而且 **一条一步、按顺序排**(例如
`1. 装依赖 2. 构建 3. 起前置服务`);
这些事 **用文字写出来**(AI 照这段文本自己按序去做)。这类前置事项往往没被写成 run configuration,所以必须在这里说明,否则 AI
直接 rerun 会拿到一个起不来的进程。 **哪个应用必须先起来**也要写明 (例如前端 dev server 的 proxy 指向本机后端)。
与本项目无关的应用不写。 **run** 写走哪条工具:常驻 / 服务化的配置一律 `rerun`(在跑就重启、没在跑就启动), **不要**用
`execute` —— 它是 Run 路径,对常驻进程会起出重复实例;细节见「跑应用只用 rerun」那条。 **port** 写清"固定 / 默认 /
被占用即启动失败";读不到就 **问用户**,不要编。 **服务化的应用一定有端口**,这一项是它区别于固定流程的地方。 **after run** 写
**起来之后才知道的结果**:日志落在哪 / 什么时候才算 ready / 起来之后要接着做什么 (要跑迁移、要把地址交给谁); **多数写
`无`**。 **热重载** 写**有没有、以及 AI 改代码后要不要重启**:有(Vite HMR / `node --watch` 这类)写清机制、改完自动生效;
无(`go run .` 这类)写明 **必须重启**。判定要有依据(运行方式 → 有没有 HMR), **不确定就问用户,不猜**。
**没有热重载的应用改完之后,不得在没有提示的情况下宣称"改动完成 / 可以去验证了"** —— 重启动作由用户做。
**desc** 写剩下的坑与依赖关系 (依赖谁、跟别的应用什么先后),以及例外 (**只在联调 / 某个流程之前才需要起**之类)。
**目录**这类配置里本来就有的字段不要单开一项 —— 会跟配置变旧而对不上。 **有 `@` 变体就在这里补一句**:有哪些变体 (如
`console-web@yutao`)。 **项名与顺序**与 `idea-run-config-manager` 那个块 **同名同序**(`before run` / `run` /
`after run` / `desc`);
本块多 `port` / `热重载`,少一项 `when`(应用名写在条目开头) —— 服务化应用就是"改完代码要起它来测"的时候起,没有别的时机可写。两个块住在同一份
`AGENTS.md` 里,名字与顺序对上了才看得出哪些是服务、哪些是固定流程。 **某项确实没有内容就写 `无`**(不省略、也不写 `-`)。

### 怎么读配置名

run configuration 的名字是 `[os@]base[@env]`,`@` 分割、最多三段:

| 段   | 位置 | 取值     | 缺省表示           |
| ---- | ---- | -------- | ------------------ |
| os   | 最前 | `win`    | macOS / Linux      |
| base | 中间 | 配置本体 | 必填               |
| env  | 最后 | 环境名   | 所有环境通用这一套 |

`win@base`(换平台)与 `base@env`(换环境)都是 `base` 的 **变种**:同一个应用、同一件事,只是平台 / 环境不同。 **这里只登记
base**,变种不另起一条、不逐个列 —— 变种怎么选见下面「怎么选变体」。

### 怎么选变体

- **平台段**按当前机器选:macOS / Linux 用 `base`,Windows 用 `win@base` —— `win@base` 不在 `get_run_configurations` 里,
  说明这个应用没有 Windows 侧的配置, **交回用户**,别拿 base 顶替。
- **环境段**:`base` 与 `base@<env>` 同时存在 = 同一件事的两套环境 → **启动前问一次用户走哪套**(问"走哪个环境",
  不是"要不要启动"); **用户选定后本会话内默认走这一套**,别反复打扰 —— 改代码 → 自己重启 → 同一套变体。
- **一个环境具体怎么接上,是项目自己的事**(启动参数 / 环境变量 / 配置文件都常见):照项目里现成的同类环境变体来,或问用户。

### 应用

- {应用名} (项目 {前缀},{base 名})
