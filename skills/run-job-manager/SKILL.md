# run-job-manager

job 就是一个 skill：`SKILL.md` 里一串按顺序执行的步骤（几步、每步做什么都由这个 job 自己决定），`assets/` 放本 job 自己的脚本（也可直接引用仓库别处已有的脚本）。
AI 加载后逐步用 `shell` 跑，任一步失败即停。

## 判据

同一件事会不会以同样的形态再发生？会（构建、生成、迁移、发布、批处理）→ 固化成 job；不会（查一条数据、看一次日志）→ 就地跑完。
常驻应用（dev server）不是 job，启停归 `idea-standalone`。

## 布局

```text
.opencode/skills/job-<名>/
├── SKILL.md        照 assets/SKILL.template.md 写
└── assets/         本 job 自己的脚本，可以不止一个（仓库别处已有脚本就直接指过去，不复制）
```

- **结构照模板，不自由发挥**：`assets/SKILL.template.md` 规定了标题层级（一级标题是 job 名，二级标题是「序号 + 简短动作名」）、要点用无序列表、命令直接作为列表的一条、只有存在系统 / 环境差异时才加表格；落盘前先读它，写完对着核一遍
- 目录名与 `name` 都带 `job-` 前缀，与 `docs-*`、`*-ops` 区分
- frontmatter 只有 `name` 与 `description`；**干什么、什么时候用、什么时候不要用只写在 description**，正文不重复——它是模型加载这个 skill 之前唯一的线索
- 正文就是一串按顺序执行的步骤，**步骤数量与形态都不固定**：每步可以是脚本、任意命令、一次工具调用，或一组连续动作，写清每步做什么即可
- 脚本自带 shebang 与可执行位，能从任意目录直接跑；正文里写路径本身，不写 `bash` 前缀

## 给已有 job 加系统 / 环境

不新建 job —— 同一个 skill 里扩展：

1. 脚本先能选：按参数或分支区分（如 `build.sh <环境>`），默认值保持现有环境，不带参数时行为不变
2. 只在**受影响的那一步**下面加表格行（系统 / 环境 → 怎么做）；没有差异的步骤不动
3. 差异不一定是换脚本：换命令、换目标地址、换配置文件都算，写在同一格里
4. 新环境的前置资产先备齐（部署目录 / compose / env、`hosts.json` 里的 deployment 映射），再写进步骤
5. description 不写环境：触发条件是「什么时候用」，环境是执行细节

## 流程

1. 查重：技能清单里已有同类 `job-*` 就改它，不新开 v2
2. 建：先读 `assets/SKILL.template.md`，按它的标题层级与结构落 `SKILL.md`（不要自创版式、不要改成纯编号列表），再放脚本
3. 删：删整个目录，不留占位

## 红线

- 一次性命令不写进 job
- 版式不照模板（标题层级、步骤编号、要点形态被改掉）视为没写完
- 需授权的动作（推迁移、动线上数据）在对应步骤里写明「必须用户授权」，AI 不自行触发
